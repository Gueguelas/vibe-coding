projetos anteriores

Nas aulas 4 a 6 o pior erro possível era um arquivo ruim no disco — git checkout . resolvia. Agora não.

1 · push é publicação

Com deploy automático, um push na branch de produção é um ato de produção. Não é um comando de versionamento — é um release. Isso muda quem pode apertar o botão.

2 · o erro fica no dado

Schema alterado por fora da migration não volta com um git revert. O código volta; a tabela fica. É a primeira vez no curso que existe estado que o git não controla.

3 · existem duas chaves

Uma pública, protegida por políticas de acesso no banco. Outra que ignora todas as políticas. A diferença entre elas é uma linha de import no arquivo errado.

e o risco principal não é o que vocês imaginam
O problema não é o agente errar. É ele acertar rápido demais.
Ele vai propor o schema inteiro, escrever as três telas e publicar — e vai ficar bom. O resultado parece certo, e é exatamente por isso que ninguém revisa. As regras de hoje não existem para impedir o agente de trabalhar mal; existem para impedir que ele trabalhe bem em cima de decisões que ninguém tomou.
a frase que organiza a aula

Antes de dar a spec, defina o contrato. Spec diz o que construir. Rule diz como se trabalha aqui — quem aprova, quem publica, o que nunca acontece. A ordem importa: contrato primeiro, porque a spec é o gatilho que coloca o agente em movimento.

# O que não fazer
> leitor: agente

## Autoridade

- Não escreva ADR. Se encontrar uma decisão que precisa de um, descreva
  a decisão e as alternativas, e PARE. Quem decide é o time.
- Não contrarie o que está em docs/adr/. Se precisar contrariar, pare.
- Não responda por conta própria o que o PRD deixou ambíguo. Liste as
  perguntas e espere.
- Não escolha biblioteca que não esteja no ADR-001. Proponha e espere.

## Escopo

- Não altere arquivo fora do escopo da tarefa atual.
- Não gere scaffold automático de framework sem mostrar antes o que ele
  vai criar.
- Não escreva código de funcionalidade sem uma spec correspondente em
  docs/specs/.

## Ritmo

- Não escreva código antes de um plano aprovado. Escreva o plano,
  mostre e espere.
- "Pode implementar" NÃO autoriza o plano inteiro: execute UMA tarefa,
  rode os checks, mostre o resultado e pare.
- Não relate sucesso parcial. Se um check falhou, a tarefa não terminou.

## Produção

- Não faça push na branch de produção. Trabalhe em branch e abra PR.
- Não rode deploy nem altere configuração da Vercel.
- Não toque no projeto Supabase remoto: nada de SQL, de alteração de
  schema ou de dado por lá. Tudo acontece no banco local.

## Precedência

- Se o código e uma spec discordarem sobre comportamento, a spec está
  certa até que alguém mude a spec.
- Se uma regra de procedimento contrariar um ADR ou uma spec, PARE e
  avise. Não escolha um dos dois por conta própria.
- "Pode ir" e "pode implementar" não revogam nada deste arquivo.
    por que este arquivo não precisa do projeto existir

    Leia de novo: ele não cita uma pasta, um comando ou uma linguagem. Autoridade independe de stack — valeria igual num projeto Python de dois anos. É por isso que ele podia ter sido o primeiro arquivo do repositório, e é por isso que ele é o primeiro agora.

    a seção Produção é nova no curso

    Ela só existe porque o deploy já está ligado. Com Vercel plugada, push é publicação — e publicar não é um procedimento a ensinar, é uma fronteira que ele não cruza. Proibição pura não vira arquivo próprio: mora aqui.

    a última linha da Precedência é a que mais salva
    Autorização no calor da tarefa não revoga o combinado
    Vai acontecer: ele pede permissão, você está com pressa, digita "pode ir" — e ele entende carta branca até o fim do plano. Essa linha faz "pode ir" significar uma tarefa, não uma sessão.

# Verificação de fim de tarefa
> leitor: agente

## Quando
Sempre que você for dizer "pronto", "implementado" ou "funcionando".

## Procedimento
1. Rode <COMANDO-TESTES>. Cole a última linha da saída na resposta.
2. Se a tarefa tocou em migration, rode `supabase db reset` local e
   confirme que o banco sobe do zero com todas as migrations.
3. Rode <COMANDO-BUILD> antes de qualquer push. Build que quebra na
   Vercel é o feedback mais lento e mais caro deste projeto.
4. Rode `git status --short`. Só podem aparecer arquivos do escopo
   da tarefa.
5. Diga qual critério de aceitação (CA-xx) esta tarefa atende.

## Verificação
Pronto = os quatro comandos terminaram sem falha E o git status não
trouxe surpresa. As duas coisas, não uma.

## Não faça
- Não relate sucesso parcial. Teste vermelho é tarefa não terminada,
  mesmo que o código "esteja certo".
- Não tente consertar a mesma falha duas vezes seguidas sem me mostrar
  a saída do erro.
- Não rode teste contra o banco remoto.
    por que esta é sempre-ligada se toda rule precisa de gatilho
    • O gatilho existe, mas não é um arquivo — é um momento. Nenhum glob captura "quando ele achar que terminou".
    • Por isso ela precisa ser das mais curtas do repositório: paga pedágio em toda mensagem.
    • O passo 3 é o que separa este projeto dos anteriores. Build local antes do push troca um ciclo de deploy quebrado por trinta segundos de espera.

# Mudança de schema
> leitor: agente

## Quando
Qualquer tarefa que precise criar, alterar ou remover tabela, coluna,
índice, constraint ou política de acesso — inclusive quando a mudança
parecer trivial.

## Procedimento
1. Antes de gerar qualquer coisa: escreva o DDL pretendido na resposta
   e PARE. Eu aprovo ou corrijo.
2. Gere a migration pela CLI: `supabase migration new <nome>`.
   Uma migration por tarefa.
3. Toda tabela nova nasce com Row Level Security habilitada e pelo
   menos uma policy explícita na mesma migration. Tabela sem policy
   não entra no repositório.
4. Se a tabela já tem dado, diga o que acontece com as linhas
   existentes. Coluna obrigatória nova precisa de default ou de um
   passo de preenchimento.
5. Aplique com `supabase db reset` local e rode <COMANDO-TESTES>.

## Verificação
`supabase db reset` numa máquina limpa aplica todas as migrations do
zero, sem erro e sem nenhum passo manual.

## Não faça
- Não altere schema pelo Studio nem por SQL avulso. O que não está em
  migration não existe.
- Não edite migration que já foi para o repositório remoto. Escreva
  a próxima.
- Não toque no projeto Supabase remoto. Tudo acontece no local.
    o passo 3 é o mais importante da aula

    Tabela sem política de acesso fica legível pela chave pública do front. O agente não vai pensar nisso sozinho porque a aplicação funciona perfeitamente assim — o buraco não tem sintoma. É o caso exemplar de regra que existe para cobrir o que funciona e mesmo assim está errado.

    o passo 1 vale mais que os outros quatro

    "Mostre e pare" transforma uma mudança difícil de desfazer numa decisão revisável de trinta segundos. É o único ponto do projeto onde vale a pena ser chato.

# Variáveis de ambiente e chaves
> leitor: agente

## Quando
Ao criar ou usar qualquer variável de ambiente, ao instanciar o client
do banco, ou ao escrever código que lê configuração.

## Procedimento
1. Chave pública (anon): só ela pode aparecer em código que roda no
   navegador. A proteção dela são as políticas de acesso do banco.
2. Chave de serviço: ignora todas as políticas. Só em código que roda
   no servidor, nunca em componente de cliente, nunca em variável com
   prefixo público.
3. Variável nova existe em TRÊS lugares ou em nenhum:
   `.env.local` (sua máquina) · `.env.example` (versionado, sem valor)
   · painel da Vercel (preview e production).
4. Ao criar uma variável, diga na resposta em quais dos três lugares
   você já a colocou e o que falta eu fazer à mão.

## Verificação
Uma busca por "service" no código que vai para o navegador não
retorna nada. `.env.example` tem todas as chaves que o projeto usa,
sem nenhum valor real.

## Não faça
- Não escreva valor de chave em resposta, commit, log ou comentário.
- Não crie variável só no `.env.local`. Ela quebra o deploy e o erro
  só aparece no build da Vercel.
- Não contorne uma política de acesso trocando de chave. Se a política
  atrapalha, a política está errada — pare e me avise.
    o passo 4 existe por um motivo específico

    O agente não tem acesso ao painel da Vercel. Uma regra que manda ele fazer o impossível é ignorada inteira — inclusive as partes que ele conseguiria cumprir. Por isso o passo pede o que está ao alcance dele: fazer o que dá e declarar o que sobrou para você.

    As três últimas,

    Essas três dependem de decisões de vocês, não minhas. Abram o acordeão, copiem o esqueleto e completem — em aula se sobrar tempo, em casa se não sobrar. Máximo 20 linhas cada. O que está lá é ponto de partida, não resposta.

    1 rules/tests.md — como se testa aqui glob ▼

    Decisões que vocês precisam fechar: o teste roda contra o banco local subido pela CLI ou contra um schema separado? Todo teste cita o CA-xx que prova? Teste de endpoint verifica só o status ou também o corpo?

    O item que quase ninguém lembra: política de acesso precisa de teste próprio — o mesmo dado, consultado com o usuário errado, não pode aparecer. É o único jeito de provar que a tabela está protegida. E esse teste não pode usar banco mocado, porque a coisa sob teste é a política, não o código.

    ponto de partida
    ## Quando
Ao escrever, alterar ou remover qualquer teste.

## Procedimento
1. Testes rodam contra o banco local. Nunca contra o remoto.
2. O nome do teste cita o critério que ele prova: test_ca_03_...
3. Teste de endpoint verifica status E corpo.
4. Tabela com política de acesso tem um teste que prova o bloqueio:
   o mesmo dado, com outro usuário, não retorna.

## Verificação
<COMANDO-TESTES> passa com o banco local recém-resetado.
    2 rules/handoff.md — fim de sessão gatilho de momento ▼

    Isto é a aula 3 virando procedimento. O que muda: agora existe estado fora do git. O handoff precisa dizer o que está commitado, e também o que está aplicado no banco local e o que já foi publicado.

    A decisão difícil é o gatilho. "Fim de sessão" é vago demais — quem decide que acabou? Fechem algo observável: ao terminar uma tarefa do plano, ao perceber que a sessão está longa, antes de trocar de assunto.

    ponto de partida
    ## Quando
Ao terminar uma tarefa do plano, ou quando eu disser "vamos fechar".

## Procedimento
Sobrescreva handoff.md na raiz com, no máximo, 25 linhas:
1. Onde parei — tarefa e critério em andamento
2. O que está commitado e em qual branch
3. O que está aplicado no banco local mas ainda não commitado
4. O que já foi publicado
5. O que NÃO fazer na próxima sessão e por quê
6. O próximo passo, em uma frase imperativa

## Verificação
Uma sessão nova, lendo só handoff.md + a spec, continua sem
perguntar nada sobre o que já foi feito.
    3 rules/spec-flow.md — abrir funcionalidade nova sob demanda ▼

    É o ciclo da aula 7 virando procedimento executável. O valor está na numeração e nos nomes de arquivo — é o que permite, daqui a dez features, achar a spec de qualquer comportamento sem procurar.

    Cuidado com o excesso: esta é a regra que mais tenta virar um manual de SDD. Ela não precisa explicar o que é uma spec. Precisa dizer onde os arquivos ficam e em que ordem nascem.

    ponto de partida
    ## Quando
Ao iniciar qualquer funcionalidade nova do PRD.

## Procedimento

2. Antes de escrever a spec, liste as perguntas que o PRD não

    Instalar dependência
    O ADR-001 fechou a stack. Uma biblioteca nova é uma decisão de arquitetura entrando pela porta dos fundos, sem alternativas avaliadas e sem ninguém saber. Se essa linha não for ao menos "pedir antes", o ADR vira decoração em duas semanas.
    o erro de calibragem mais comum

    Marcar tudo como "pedir antes". Um agente que pede permissão para editar o arquivo da própria tarefa é inútil — e o efeito colateral é você começar a aprovar no automático, que é o mesmo que não aprovar. Aprovação só protege enquanto for rara o suficiente para você ler.

    Qual modelo
    em cada fase

    Esta é a regra cujo leitor é você, não o agente — ele não escolhe o próprio modelo nem o próprio nível de raciocínio. É checklist de operador, e por isso vai marcada como tal no arquivo.

    Escrever a spectexto curto, decisão cara, governa semanas
    Planejar e quebrar em tarefasdefine a ordem de ataque e o que é uma tarefa
    Executar uma tarefa já decididavolume: o que fazer já está escrito
    Debugar algo que quebroudecisão cara disfarçada de execução
    Revisar o diff antes do commitde preferência em sessão limpa
    a lógica por trás

    Raciocínio alto compensa onde o texto é curto e a decisão é cara — spec e plano cabem numa página e governam semanas. Executar tarefa já decidida é volume: o ganho de um modelo mais lento é pequeno e o custo é real. Debugar volta a ser decisão cara disfarçada de execução.

    o truque que poucos usam

    Revisar com um modelo diferente do que escreveu, em sessão limpa, sem o histórico da implementação. Quem escreveu já está convencido — e a sessão inteira é um argumento a favor do próprio código. Modelo novo lê o diff como um revisor leria: sem contexto emocional e sem saber o que "era para" estar lá.

    por que isso é uma regra e não uma preferência

    Porque sem estar escrito, todo mundo usa o modelo mais rápido para tudo — inclusive para a spec, que é onde o erro custa mais caro. A regra não é sobre o modelo ser melhor; é sobre você não decidir isso no impulso, às onze da noite, no meio de uma tarefa.

    o que vocês têm agora

    Um repositório instruído: contexto, limite de autoridade e contrato. Ele responde "como se trabalha aqui" — e é o que impede a próxima aula de virar o agente construindo sozinho enquanto vocês assistem.

    o que ainda falta, e vem depois

    Nenhum arquivo de hoje diz como o código deve ser escrito: padrão de camada, documentação, princípios de design. Isso é outra categoria, com outro nome — e a gente só vai escrever depois de ter código de verdade para apontar.
