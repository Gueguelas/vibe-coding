Mesma situação da aula 3: o agente não lembra de nada. A diferença é que dessa vez vocês deixaram o repositório preparado — e hoje a gente descobre se aquilo funciona.

💭 Abram um chat novo, no mesmo repositório da aula passada. Não recuperem a conversa anterior. O handoff que vocês geraram é a única ponte — se ele estiver ruim, a aula de hoje começa travada. Isso não é acidente do roteiro: é o teste.

anatomia da retomada

O que cada seção
fez por você

A retomada não foi mágica. Cada seção resolveu um problema específico — e repare que o formato daquelas seções não veio do prompt: veio do rules/handoff.md que vocês criaram no passo 8.

seção 1 · onde parei
Deu o estado, não o histórico
Em duas frases o agente soube que os ADRs existem, que o plano está escrito e revisado, e que nenhuma linha de código foi escrita. Sem isso, ele começaria propondo arquitetura — como fez no passo 2 da aula passada.
seção 2 · decisões não óbvias
Apontou, não repetiu
A regra "não repita nada que já esteja no AGENTS.md, em rules/ ou nos ADRs" fez ele escrever "ver ADR-002" em vez de copiar o raciocínio inteiro. Uma fonte só — e ela é a versionada.
seção 3 · o que tentei e não funcionou
Evitou a discussão de novo
Se alguém registrou "campo de saldo foi descartado, não sugerir de novo", o agente não vai reabrir. Sem isso ele reabriria — com o mesmo entusiasmo da semana passada, porque para ele é a primeira vez.
seção 4 · próximo passo exato
Foi o que economizou os dez minutos
"Executar a etapa 1 do plano: entidade de lançamento" é acionável. "Continuar a implementação" teria devolvido uma pergunta, e vocês estariam explicando o projeto de novo agora.

🎯 E o que o handoff NÃO precisou dizer: como se trabalha no projeto (AGENTS.md), por que o saldo é calculado (ADR-002), como escrever teste (rules/tests.md). Meia página bastou porque as outras memórias existiam. É por isso que separar as três não é preciosismo.

teste 4 · o momento da aula

Consulte o saldo
em 2027

# hoje curl "localhost:8000/clientes/42/saldo?em=2026-08-14" → saldo 320, um lote expirado # daqui a um ano curl "localhost:8000/clientes/42/saldo?em=2027-08-14" → saldo menor, mais lotes expirados # e no passado, antes de tudo expirar curl "localhost:8000/clientes/42/saldo?em=2025-06-01" → o saldo que o cliente tinha naquele dia

Dá para fazer o mesmo pela tela, mudando o campo saldo em — mais visual para a turma inteira acompanhar.

🎯 Isso é impossível com um campo saldo INT. Não é difícil, não é lento — é impossível, porque a informação de ontem foi sobrescrita e não existe em lugar nenhum. O ADR-002 deixou de ser argumento de slide e virou uma resposta HTTP.

📊 E é assim que o Financeiro fecha o mês: ?em=2026-07-31 devolve o passivo daquela data, auditável meses depois. Vocês implementaram um requisito do PRD sem ter escrito uma linha específica para ele — ele caiu de graça do desenho certo.

não existe

Vocês acabaram de adicionar banco de dados, servidor HTTP e uma interface web. Vejam o que isso mudou na regra de negócio.

# compare o commit do domínio com o de agora git log --oneline git diff <commit-da-etapa-2> HEAD --stat -- src/pontos/dominio/ # resultado esperado: vazio.
🧩 A tela inteira entrou sem tocar uma linha de regra de negócio. Isso é o ADR-001 se pagando. Quando vocês leram aquele ADR, o benefício era abstrato — "testa sem banco, troca de interface sem tocar regra". Agora é um comando que retorna vazio.

# Decisões de arquitetura

Índice das decisões deste projeto. Leia este arquivo antes de propor
mudanças estruturais. Abra o ADR completo só quando precisar do
raciocínio por trás da decisão.

| #   | Decisão                             | Status |
|-----|-------------------------------------|--------|
| 001 | Domínio isolado de infraestrutura   | aceito |
| 002 | Pontos como lançamentos imutáveis   | aceito |

O número 003 não existe. O arquivo registrava a expiração de 12 meses,
que é requisito do PRD e não decisão do time — foi removido, e o número
não será reaproveitado.

🧹 Por que apagar, se ADR é append-only? Porque a regra do append-only protege decisões. O 003 nunca foi uma — não existe raciocínio a preservar ali, existe um erro de classificação. Superar seria fingir que houve uma decisão onde não houve. Mas o buraco fica registrado no índice: quem chegar depois precisa saber que o 003 sumiu de propósito.

o risco que isso evita

Registrar requisito como decisão é pior que não registrar: dá a impressão de que dá para mudar. Alguém — ou algum agente — olha aquele ADR daqui a seis meses, acha que 12 meses foi escolha arbitrária da engenharia e "otimiza" para 6. E aí vocês têm um problema com o Marketing, com o Financeiro e possivelmente com o Procon.

git add -A && git commit -m "chore: remove ADR-003, requisito nao e decisao"
projetem lado a lado

Três ferramentas,
um sistema

Três pessoas de harnesses diferentes projetam a estrutura de pastas e a tela. O código literal não vai ser idêntico — e não é isso que importa. Comparem estas quatro dimensões:

Modelo de domínio — todos guardam lançamentos, ninguém tem campo de saldo
Fronteira de módulos — todos têm domínio sem import de infraestrutura
Formato dos testes — datas fixas, sem banco, um cenário por teste
Decisões — mesmos ADRs, mesmo raciocínio, mesma pendência registrada
🎯 Na aula passada, no passo 2, vocês eram seis arquiteturas diferentes lendo o mesmo PRD. Agora são seis implementações equivalentes — com as mesmas ferramentas de antes. Nada mudou no harness. Mudou o que estava escrito no repositório.
